Capital Bikeshare — Next-Day Rentals Forecast

NUS ISS Assignment · UCI Bike Sharing Dataset (2011–2012) · MLOps experiment tracking with MLflow

1. Problem

Every evening the operations team needs an estimate of tomorrow's total rentals to plan staffing and fleet capacity. An estimate that is too low leaves the team unprepared for a busy day; too high raises unnecessary operating costs. Only information available that evening may be used, and the model is compared against a simple naive rule: tomorrow = yesterday.

2. Approach

  • Time-based split: train on all of 2011 (358 days), test on all of 2012 (366 days); no shuffling, so no future information leaks into training.
  • Leakage guard: drop casual and registered — their sum is exactly the target cnt.
  • Legitimate features: lag1 (yesterday's rentals, known that evening), lag7 (same day last week), weathersit (weather situation).
  • Two analysts: A = plain autoregressive AR(1) (lag1 only); B = adds the weekly lag and weather situation. Both are Ridge regressions (pure-numpy implementation with drop-first one-hot and z-score scaling).
  • Traceable (MLflow): every run logs data period, features, hyper-parameters, metrics and tags via mlflow.log_params / log_metrics / set_tag / log_input; the best model is registered as a named version BikeShareForecaster (currently v2) via mlflow.register_model.

3. MLflow Tracking & Model Registry

The local tracking store is sqlite:///mlflow.db, under experiment CapitalBikeshare. Parameters, metrics and tags for both runs are persisted, and the best model is registered in the Model Registry. To explore locally:

python src/train.py      # run experiments and log to MLflow
mlflow ui                # open http://127.0.0.1:5000 to browse runs & registered models
  • Runs: analystA_ar1 and analystB_weather — compare RMSE, features and hyper-parameters side by side.
  • Model Registry: BikeShareForecaster has named versions v1 and v2 — retrievable and reproducible.
